# Expert Call Analyzer — Hasamex AI Engineer Case Study

Analyzes 3 expert-call transcripts (European robotic surgery market) against
an interview guide, extracts cited quotes with timestamps, surfaces common
themes and disagreements across experts, and answers free-form questions
across all transcripts.

## Quick start

```bash
git clone <this-repo>
cd hasamex-case-study
pip install -r requirements.txt
cp .env.example .env   # then paste your ANTHROPIC_API_KEY into .env
streamlit run app.py
```

The app opens at `http://localhost:8501`. The 3 provided transcripts and the
interview guide are already bundled in `data/`.

## What it does

| Tab | What it shows |
|---|---|
| **Per-Expert Answers** | Runs every interview-guide question against one chosen expert's transcript, with the exact quote + timestamp backing each answer |
| **Common Themes & Disagreements** | Cross-references all 3 experts to find where they agree and where they meaningfully diverge, each claim cited per expert |
| **Ask a Question** | Free-text Q&A across all transcripts, same grounding/citation guarantee |
| **Raw Transcripts** | The parsed source, for manually spot-checking any answer |

## Architecture

```
data/*.txt  →  transcript_parser.py  →  QASegment[]  →  retrieval.py (TF-IDF)
                                                              │
                                                    top-k relevant segments
                                                              │
                                                        llm_engine.py
                                                    (Claude, grounded prompt,
                                                     JSON output, quote check)
                                                              │
                                                           app.py (Streamlit)
```

1. **`transcript_parser.py`** — deterministic, no LLM involved. Splits each
   transcript into `(timestamp, question, answer, expert, market)` segments.
   This is the single source of truth for every quote/timestamp shown later.
2. **`retrieval.py`** — a small pure-Python TF-IDF + cosine-similarity index.
   Given a question, returns the most relevant segments (optionally filtered
   to one expert). This keeps prompts focused instead of dumping every
   transcript into every call.
3. **`llm_engine.py`** — the only place that talks to Claude. Every prompt:
   - Includes **only** the retrieved segments (never "answer from memory")
   - Forces **structured JSON output** (`answer`, `citations[]` with
     `quote`/`timestamp`/`source_file`)
   - Is followed by **`verify_quote()`**, which checks each returned quote is
     an actual (near-)verbatim substring of the segment it claims to cite.
     Unverified quotes are flagged `⚠️` in the UI instead of trusted blindly.
4. **`app.py`** — Streamlit UI that wires the three layers together and
   renders citations next to every claim.

## Model choice

Claude (Sonnet) via the Anthropic Messages API, for two reasons specific to
this task: strong instruction-following on "only answer from the provided
text" style constraints, and reliable structured JSON output, which the
whole citation/verification pipeline depends on. The model is swappable —
`llm_engine.py` isolates all API calls behind three functions
(`answer_question_for_expert`, `cross_transcript_themes`,
`ask_freeform_question`), so pointing them at a different provider only
touches one file.

## How citations/timestamps are handled

Timestamps are never generated by the LLM — they're parsed directly from the
transcript text by `transcript_parser.py` and attached to each segment
before the LLM ever sees them. The model is only asked to pick which
retrieved segment(s) support its answer and to copy the quote verbatim; it
cannot invent a timestamp because it never produces one, it only echoes
metadata that was handed to it. The `verify_quote()` step then double-checks
the echoed quote is actually present in that segment's text.

## How hallucinations are reduced

1. **Retrieval grounding** — the model only ever sees the segments the
   retriever selected, never asked to recall transcript content from
   context alone.
2. **Explicit "not mentioned" escape hatch** — the system prompt tells the
   model it's expected to say a topic wasn't discussed rather than guess.
3. **Verbatim-quote requirement + post-hoc verification** — every claim
   must carry a quote, and that quote is checked against the source text
   after generation; unverified quotes are visibly flagged rather than
   silently displayed.
4. **Structured JSON output** — much harder for a model to blend
   speculation into a rigid schema than into free-flowing prose.

## Scaling from 3 transcripts to 30+

The architecture is already split so this is a swap, not a rewrite:

- **Retrieval**: replace `retrieval.py`'s TF-IDF index with real embeddings
  (e.g. `voyage-3` or OpenAI embeddings) stored in a vector DB (Chroma,
  pgvector, or Pinecone). The `TfidfIndex.search()` interface stays the
  same, so `app.py` and `llm_engine.py` don't need to change.
- **Chunking**: segments are already small, timestamped units — this holds
  up fine at scale; would add overlap/window tuning if answers spanned
  multiple turns.
- **Cross-transcript analysis**: at 30+ transcripts you can't put every
  segment in one prompt. Switch to a map-reduce pattern — cluster/theme
  each transcript individually first (map), then synthesize a second pass
  over those per-transcript summaries (reduce) — rather than one giant
  cross-transcript call.
- **Caching**: cache LLM responses per (question, segment-set) hash so
  re-running the per-expert tab doesn't re-call the API for unchanged data.
- **Async/batch**: parallelize per-expert and per-question calls (they're
  independent) instead of the current sequential loop.

## Known limitations

- TF-IDF retrieval is intentionally simple for a 3-transcript corpus; it
  would be replaced by semantic embeddings at scale (see above).
- Quote verification uses substring + fuzzy match, so minor LLM
  whitespace/punctuation drift can occasionally still pass; a stricter
  exact-match mode is a one-line change in `verify_quote()`.
- No persistence layer — each Streamlit session re-parses the transcripts
  (fast at this scale; would add a DB at 30+ transcripts).
